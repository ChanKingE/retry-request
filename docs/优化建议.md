## 3. P0：发布前必须解决

### P0-1 发布声明引用未发布的 `RequiredPick`（已完成）

**分类：已确认缺陷**

**现状证据**

- `src/types.ts:176` 使用全局 `RequiredPick` 定义 `InterceptorRequestOptions`。
- `RequiredPick` 只定义在 `types/global.d.ts:5`。
- 生成的 `dist/index.d.mts:268` 仍直接引用 `RequiredPick`，没有将其定义内联到声明文件。
- `package.json` 的 `files` 只发布 `dist`，实际 dry-run 包中也没有 `types/global.d.ts`。

因此，一个没有自行声明 `RequiredPick` 的消费者读取 `dist/index.d.mts` 时，可能出现
`Cannot find name 'RequiredPick'`。仓库内 `vp check` 能通过，是因为本仓库能够读取
`types/global.d.ts`，不能证明发布包中的声明文件完整。

**影响**

- TypeScript 消费者可能无法完成类型检查。
- 开启 `skipLibCheck` 的消费者可能暂时看不到问题，但缺陷仍存在。
- 这是发布产物契约问题，应阻止当前版本发布。

**建议改法**

1. 在 `src/types.ts` 内定义局部类型，例如：

   ```ts
   type RequiredRequestFields<T, K extends keyof T> = Omit<T, K> & Required<Pick<T, K>>;
   ```

   也可以在 `InterceptorRequestOptions` 上直接组合 `Omit` 和 `Required<Pick>`，避免增加公共导出。

2. 删除 `types/global.d.ts` 中没有其他使用者的 `RequiredPick`、`DeepRequired`、`PartialPick`、
   `DeepPartial`，避免向使用该仓库源码的项目注入全局类型。
3. 增加一个独立的消费者类型测试，只从打包产物导入：
   - `ClientOptions`
   - `RequestOptions`
   - `InterceptorRequestOptions`
   - `createHttpClient`

**兼容性**

- 只要保持 `InterceptorRequestOptions` 的最终结构不变，对正常消费者应为兼容修复。
- 如果有人依赖本仓库隐式注入的四个全局工具类型，删除它们会影响该非公开用法；不应为这种隐式
  全局污染继续提供兼容。

**验收测试**

- 重新打包后，`rg "RequiredPick" dist/index.d.mts` 不应命中未声明的类型名。
- 在一个不加载仓库 `types/global.d.ts` 的临时 TypeScript 项目中导入发布产物，`tsc --noEmit`
  必须通过。
- `vp check`、`vp test`、`vp run build` 全部通过。

**实施结果**

- `RequiredPick` 已收回 `src/types.ts` 模块作用域，生成声明包含自身依赖。
- 已删除未发布且未使用的全局工具类型文件。
- 已新增 `test:published-types`，构建后从 `dist/index.mjs` 导入公共类型并独立执行严格类型检查。

## 4. P1：正确性、安全与一致性

### P1-1 消除 helpers 与 client 的运行时循环依赖（已完成）

**分类：已确认风险**

**现状证据**

- `src/helpers.ts:2` 运行时导入 `RequestClient`。
- `src/client.ts:2` 运行时从 `helpers.ts` 导入 `resolveURL`。
- Axios、UniApp、Mock 和去重插件也从 `helpers.ts` 导入底层工具。

这形成 `helpers -> client -> helpers` 的循环。当前 ESM 打包和测试可以运行，但模块初始化顺序
已经与工厂函数、默认客户端初始化绑定，后续增加顶层状态时容易出现未初始化绑定错误。

**影响**

- 增加源码直跑、测试转换器和不同打包器之间的行为风险。
- `helpers.ts` 同时承担公共工厂、响应解包、URL 和取消工具，职责过多。

**建议改法**

- 保留用户指定的 `createHttpClient` 在 `helpers.ts`。
- 新建无业务依赖的内部工具模块，例如 `src/internal/request-utils.ts`，放置：
  - `resolveURL`
  - `getAbortReason`
  - 后续共享的查询参数处理函数
- `client.ts`、适配器和插件直接依赖内部工具模块。
- `helpers.ts` 可以重新导出仍属于公共 API 的工具，但内部模块不得导入 `RequestClient`。

**兼容性**

- `createHttpClient`、`resolveURL`、`getAbortReason` 的包入口导出保持不变时，对消费者兼容。
- 这是内部模块重组，不应新增公开子路径。

**验收测试**

- 静态导入图中不存在 `helpers.ts <-> client.ts` 环。
- 从包入口和 `src/helpers.ts` 分别导入 `createHttpClient` 均可创建客户端。
- 默认 `httpClient` 初始化、全部测试和构建通过。

**实施结果**

- 已新增内部纯工具模块，客户端、适配器和插件不再运行时依赖 `helpers.ts`。
- `helpers.ts` 继续从公共入口导出 `resolveURL` 和 `getAbortReason`，现有导入保持兼容。

### P1-2 统一取消错误和请求前置检查（已完成）

**分类：已确认缺陷**

**现状证据**

- `src/retry.ts:102` 在重试等待中直接拒绝 `signal.reason`。
- `src/plugins/mock/utils.ts:25` 在 Mock 延迟中直接拒绝 `signal.reason`。
- `src/helpers.ts:133` 已存在 `getAbortReason`，但只在部分适配器和去重复用路径中使用。
- `RequestClient.request` 在请求拦截器、解析器或自定义适配器执行前没有统一检查已取消信号。
- 当 `AbortController.abort()` 接收字符串、对象或普通 `Error` 时，不同路径可能分别抛出原值、
  `AbortError` 或最终被标准化为 `NetworkError`。

**影响**

- 调用方无法稳定使用 `isAbortError` 判断主动取消。
- 已取消请求仍可能进入 Mock、自定义 resolver 或忽略 signal 的自定义 adapter。
- 取消发生在不同阶段时，错误类型可能不同。

**建议改法**

- 所有取消路径统一调用一个内部函数，将取消结果规范为 `name === "AbortError"` 的 `Error`。
- 保留原始 `signal.reason` 作为 `cause`；如果 reason 已经是 `AbortError`，原样返回。
- `RequestClient` 在请求拦截器完成后、每次传输尝试前检查 signal。
- retry wait、Mock wait、去重复用等待、Fetch、Axios、UniApp 使用同一转换函数。

**兼容性**

- 普通 `abort()` 的行为不变。
- 过去依赖直接抛出字符串或自定义普通 Error 的代码会看到统一的 `AbortError`，需要在变更说明中
  明确，但该变化能修正当前文档承诺。

**验收测试**

- 覆盖 `abort()`、`abort("reason")`、`abort(new Error("reason"))`。
- 覆盖请求前取消、请求中取消、重试等待取消、Mock 延迟取消和去重复用者取消。
- 所有路径均满足 `isAbortError(error) === true`，并能从 `cause` 读取原始原因。
- 已取消请求不会调用 resolver 或 adapter。

**实施结果**

- 重试、Mock、Fetch、Axios、UniApp 和去重复用路径已统一产生 `AbortError`，原始 reason 保存在
  `cause`。
- 已取消信号会在 resolver 和 adapter 执行前退出，并有回归测试覆盖。

### P1-3 修正 UniApp 取消与超时的竞争顺序（已完成）

**分类：已确认控制流风险**

**现状证据**

- `src/adapter/uniapp.adapter.ts:218` 的外部取消处理先执行 `task.abort()`，之后才调用
  `rejectOnce(getAbortReason(...))`。
- `src/adapter/uniapp.adapter.ts:271` 的本地超时同样先执行 `task.abort()`，之后才拒绝
  `TimeoutError`。
- 某些 `uni.request` 实现会在 `abort()` 中同步触发 `fail`；此时 `fail` 可以先把 Promise
  确定为 `NetworkError`，预期的取消或超时错误随后会被 `settled` 忽略。

**影响**

- 相同的取消或超时在不同 UniApp 平台上可能得到不同错误类型。
- 上层重试判断可能把一次主动取消误判为网络错误。

**建议改法**

- 外部取消时先通过 `rejectOnce` 锁定 `AbortError`，再调用 `task.abort()`。
- 本地超时时先锁定 `TimeoutError`，再调用 `task.abort()`。
- `fail` 回调在 `abortRequested` 或已经 settled 时直接返回。

**兼容性**

- 修正错误分类，不改变请求参数或成功响应。

**验收测试**

- 构造 `abort()` 内同步调用 `options.fail()` 的 UniRequest 测试替身。
- 外部取消必须得到 `AbortError`，本地超时必须得到 `TimeoutError`。
- `abort()` 只调用一次，完成后的回调不得二次改变结果。

**实施结果**

- UniApp 已改为先结算 `AbortError` 或 `TimeoutError`，再调用底层 `abort()`。
- 新测试模拟了 `abort()` 同步触发 `fail` 的运行时行为。

### P1-4 正确处理带 hash 的 URL 查询参数（已完成）

**分类：已确认缺陷**

**现状证据**

- `src/adapter/fetch.adapter.ts:89` 和 `src/adapter/uniapp.adapter.ts:290` 分别维护查询参数拼接逻辑。
- 两处均直接在完整 URL 末尾追加 `?` 或 `&`。
- 对 `/items#detail` 追加 `{ page: 1 }` 会得到 `/items#detail?page=1`，查询参数位于 fragment
  后面，不会作为 HTTP 查询参数发送。

**影响**

- 带 fragment 的请求会丢失查询参数。
- Fetch 和 UniApp 复制了相近实现，后续修复容易再次出现差异。

**建议改法**

- 把 URL 拆分为 fragment 前后的两部分，只在 fragment 前插入查询字符串。
- 抽取共享查询参数函数，Fetch 和 UniApp 复用同一实现。
- 明确支持对象、数组和 `URLSearchParams` 的范围；不能跨适配器一致支持的类型应在类型和文档中说明。

**兼容性**

- 不带 hash 的现有 URL 行为保持不变。
- 属于错误修复。

**验收测试**

- 覆盖无查询、有既有查询、有 hash、既有查询加 hash、空参数和数组参数。
- Fetch 与 UniApp 对相同输入生成相同 URL。

**实施结果**

- Fetch 与 UniApp 已共享查询参数实现，参数插入 fragment 之前。
- 实现不要求 UniApp 运行时提供 `URLSearchParams`，并保持空格编码为 `+`。

### P1-5 扩展 Fetch JSON 媒体类型识别（已完成）

**分类：已确认适配差异**

**现状证据**

- `src/adapter/fetch.adapter.ts:135` 只在 Content-Type 包含 `application/json` 时解析 JSON。
- `application/problem+json`、`application/vnd.api+json` 等标准 JSON 派生媒体类型会被返回为字符串。

**影响**

- 调用方声明的响应泛型与运行时数据不一致。
- 错误响应常使用 `application/problem+json`，当前会失去结构化错误体。

**建议改法**

- 解析去除参数后的媒体类型，接受 `application/json` 和以 `+json` 结尾的类型。
- 明确 JSON 解析失败的策略：建议保留 `SyntaxError` 并附加响应上下文，不要归类为网络错误。
- 后续如需 Blob、ArrayBuffer 或流式响应，单独设计显式 `responseType`，不要依据响应泛型猜测。

**兼容性**

- `+json` 响应将从字符串变为对象，属于符合 Content-Type 语义的修复。

**验收测试**

- 覆盖 `application/json; charset=utf-8`、`application/problem+json`、普通文本、空响应和非法 JSON。
- 非 JSON 响应继续返回文本。

**实施结果**

- Fetch 已支持 `application/json` 和 `application/*+json`，包括带 charset 参数的响应。
- 新测试覆盖 `application/problem+json`。

### P1-6 阻止 AxiosAdapter 泄漏插件和业务字段（已完成）

**分类：已确认风险**

**现状证据**

- `src/adapter/axios.adapter.ts:103-108` 依次展开 adapterOptions、requestConfig 和完整 `config`。
- `RequestOptionsExtensions` 允许加入任意业务字段；内置插件已经加入 `dedupe`、`mock`、`logger`。
- 因此这些字段会作为未知 Axios 配置传入底层实例，而 Fetch 和 UniApp 不会这样做。

**影响**

- 不同适配器对同一 RequestOptions 的透传行为不一致。
- 自定义 Axios 拦截器可能意外读取、序列化或记录插件配置和业务敏感字段。
- Axios 升级后，未知字段可能与新增官方字段冲突。

**建议改法**

- 从 RequestOptions 白名单映射 `url`、`method`、`params`、`data`、`headers`、`timeout`、
  `withCredentials` 和 `signal`。
- Axios 专属字段只允许通过 `AxiosAdapterOptions.requestConfig` 传入。
- 明确优先级为：adapter 默认配置 < `requestConfig` < 受控请求字段。

**兼容性**

- 依赖“在 RequestOptions 上声明 Axios 私有字段并自动透传”的代码会受影响。
- 应提供迁移说明：将这类字段移动到 `requestConfig`。

**验收测试**

- 在请求配置中加入 `mock`、`logger`、`dedupe` 和声明合并字段，断言 Axios 收不到这些字段。
- 断言 `requestConfig` 中的 `responseType` 等 Axios 专属字段仍正常传递。
- 断言核心请求字段继续覆盖 adapter 默认配置。

**实施结果**

- AxiosAdapter 已改为白名单映射统一请求字段。
- 未提供的可选字段不会以 `undefined` 覆盖 `requestConfig`，GET/HEAD 会明确移除默认 data。
- 插件字段和声明合并业务字段不再传给 Axios。

### P1-7 取消 UniApp PATCH 的静默语义转换

**分类：已确认行为，涉及破坏性决策**

**现状证据**

- 公共 `HttpMethod` 包含 PATCH。
- `src/adapter/uniapp.adapter.ts:93` 明确声明 PATCH 会降级为 POST。
- `src/adapter/uniapp.adapter.ts:316` 实际返回 `POST`，没有通知调用方，也没有自动添加
  method override 标记。

**影响**

- 服务端可能把 PATCH 当作完全不同的 POST 操作。
- 调用方从类型和方法名无法判断实际发出的 HTTP 方法。

**建议改法**

- 推荐默认遇到 PATCH 时抛出明确的配置错误。
- 如果项目确实需要 method override，在 `UniAppAdapterOptions` 增加显式策略，例如：
  `patchMode: "reject" | "post-override"`，默认 `reject`。
- 选择 `post-override` 时同时发送约定的 override header，并在文档中说明需要服务端支持。

**兼容性**

- 改变现有 PATCH 行为，必须作为破坏性变更发布。
- 在实施前应确认目标 UniApp 平台的实际方法支持范围。

**验收测试**

- 默认 PATCH 不调用 `uni.request`，而是抛出可识别的配置错误。
- 显式 override 模式发送 POST 和正确的 override header。
- 其他方法保持原映射。

### P1-8 为日志插件增加默认脱敏（已完成）

**分类：已确认安全风险**

**现状证据**

- `src/plugins/logger.ts:42` 将完整请求配置传给 `logger.debug`。
- `src/plugins/logger.ts:49` 记录完整响应数据。
- `src/plugins/logger.ts:54` 记录完整错误对象。
- 请求配置可能包含 Authorization、Cookie、查询参数、请求体以及插件或业务扩展字段。

**影响**

- 开发控制台、远程日志平台或错误采集系统可能保存访问令牌、Cookie、个人信息和业务数据。
- 自定义 logger 通常会把对象发送到外部服务，风险不局限于本地开发环境。

**建议改法**

- 默认脱敏大小写不敏感的 `authorization`、`proxy-authorization`、`cookie`、`set-cookie`、
  `x-api-key` 等字段。
- 增加 `redact` 或 `serialize` 回调，让调用方扩展业务字段脱敏。
- 增加是否记录 request body、response body 的开关，生产环境建议默认关闭正文。
- 不修改原始 config 或 response，日志对象必须是快照。

**兼容性**

- 日志内容会变化，但请求行为不变。
- 新选项应保持现有 logger 接口可用。

**验收测试**

- 大小写不同的敏感 header 均被替换为固定占位符。
- 原请求配置不被修改。
- 自定义 redactor、关闭正文和插件卸载行为均有测试。

**实施结果**

- 默认脱敏敏感 header，并默认隐藏请求体、响应体和错误详情正文。
- 新增 `redactHeaders`、`logRequestBody`、`logResponseBody`，支持插件级和单次请求覆盖。

## 5. P2：维护性与后续 API 设计

### P2-1 统一 RequestClient 构造器默认值

**分类：已确认差异**

**现状证据**

- `src/client.ts:53-59` 只在第二参数完全省略时使用 `{ headers: {}, timeout: 30_000 }`。
- `new RequestClient(adapter, {})` 会跳过该默认对象，最终没有 30 秒超时。
- 构造器第二参数使用 `ClientOptions`，因此允许再次传入 `adapter`；该字段会进入 defaults，并可能
  被展开到最终请求配置。
- `createHttpClient` 的默认超时另为 10 秒。

**影响**

- `{}` 是否显式传入会改变超时行为。
- 直接构造和工厂构造的默认值关系不够清晰。
- `adapter` 出现在构造器 defaults 中没有意义。

**建议改法**

- 构造器第二参数改为 `CommonOptions`。
- 明确一种默认策略：推荐 `RequestClient` 自身不注入超时，只有 `createHttpClient` 提供 10 秒默认值。
- 如果必须保留直接构造的 30 秒超时，则无论是否传 `{}` 都应统一合并。
- 在构造器和工厂文档中分别写清默认值来源。

**兼容性**

- 改变直接构造器默认超时可能影响请求持续时间，应在发布说明中列出。
- 将参数类型从 ClientOptions 收窄为 CommonOptions 只会影响错误地传入 adapter 的调用。

**验收测试**

- 覆盖省略 defaults、传 `{}`、只传 baseURL、显式 timeout 和工厂默认值。
- 最终适配器配置中不得出现 `adapter` 字段。

### P2-4 评估拆分 params 与 data 泛型

**分类：设计改进候选**

**现状证据**

- 当前 `RequestOptions<TBody>` 同时把 `params` 和 `data` 定义为 `Partial<TBody>`。
- 同一次请求需要不同查询参数和请求体时，只能使用交叉类型或宽泛对象，无法阻止查询字段进入
  data、请求体字段进入 params。
- FetchAdapter 实际还支持 string、Blob、FormData、URLSearchParams、ArrayBuffer 和 TypedArray，
  `Partial<TBody>` 不能准确表达这些原生请求体。

**影响**

- 通用 `request` 方法的类型安全弱于运行时能力。
- 扩展二进制上传或表单请求时需要类型规避。

**建议改法**

- 在破坏性版本中评估 `RequestOptions<TParams, TData>`：

  ```ts
  interface RequestOptions<TParams = Record<string, unknown>, TData = unknown> {
    params?: TParams;
    data?: TData;
  }
  ```

- GET 类快捷方法只暴露 TParams，写方法主要暴露 TData，同时 config 仍可指定查询参数泛型。
- 为旧单泛型调用提供迁移示例，不同时保留两套含义模糊的泛型顺序。

**兼容性**

- 会改变公共类型参数数量和推断结果，必须作为破坏性变更。
- 实施前应先修正文档，避免再次出现源码与指南不一致。

**验收测试**

- 增加 `expectTypeOf` 或独立 `.test-d.ts` 用例。
- 验证 JSON body、FormData、Blob、独立 params/data、快捷方法和 config-only overload。

### P2-5 完善去重和一次性 Mock 的并发边界

**分类：已确认边界与设计改进候选**

**现状证据**

- 去重插件复用首个请求产生的 Promise。重复调用者取消只停止自己的等待，但首个请求的 signal
  仍控制共享底层请求；首个调用者取消会让所有复用者失败。
- `cacheSettled: true` 时，entries 只按时间清理，没有容量上限；高基数请求和长 windowMs 会增加
  内存占用。
- Mock 插件在异步匹配完成后才于 `src/plugins/mock/plugin.ts:86` 标记 once 路由已消费；两个并发
  请求可能在标记前同时匹配同一路由。

**影响**

- 去重调用者之间的取消语义不对称。
- 长窗口缓存可能形成短期内存压力。
- `once` Mock 在并发测试中不一定真的只使用一次。

**建议改法**

- 在文档中先明确首请求拥有底层传输的现有语义。
- 如果需要调用者完全独立，使用插件内部 AbortController 和引用计数：所有等待者都取消后再中止底层请求。
- 为 settled cache 增加可选 `maxEntries`，采用确定性的淘汰策略。
- once Mock 路由需要在确定命中时原子预留；工厂失败时是否恢复路由必须形成明确规则。

**兼容性**

- 改变首请求取消语义和 once 工厂失败策略可能影响现有测试，应作为功能变更记录。
- `maxEntries` 可作为兼容新增选项。

**验收测试**

- 覆盖首调用者取消、重复调用者取消、全部调用者取消和底层 adapter 调用次数。
- 覆盖缓存容量淘汰。
- 两个并发请求只能有一个消费 once Mock 路由。

### P2-6 清理失效 API 和低风险维护项

**分类：维护性改进**

**现状证据**

- `HttpAdapter.abort(requestId)` 存在于公共接口，但客户端没有 requestId，也不会调用该方法。
- `types/global.d.ts` 的四个工具类型中只有 `RequiredPick` 被使用。
- `src/client.ts:99` 的公开注释仍包含 TODO。
- `interceptors` getter 每次访问都创建新对象和新的 bind 函数。
- `mergeHeaders` 对每个覆盖项重复扫描现有 header 键，复杂度为 O(n*m)。

**建议改法**

- 删除未接入的 `HttpAdapter.abort`，或先设计完整 requestId 契约后再实现；不要保留无法兑现的接口。
- 移除全局工具类型，局部定义真正需要的类型组合。
- 将 TODO 转为确定的 API 文档或独立任务。
- 把 `interceptors` 作为构造时初始化的稳定只读属性，确保引用稳定。
- 使用小写键索引一次性合并 headers，同时保留调用方最后一次传入的原始键名。

**兼容性**

- 删除 `HttpAdapter.abort` 是类型层面的破坏性变更，应与其他主版本调整合并。
- 其余项目可以保持公共行为兼容。

**验收测试**

- 连续读取 `client.interceptors` 返回同一引用。
- header 覆盖继续大小写不敏感，且不修改输入对象。
- 发布声明不再包含无实现承诺的 abort API 和未解析的全局类型。
